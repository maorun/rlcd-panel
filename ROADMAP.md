# Roadmap

This file lists open work for `rlcd-panel`, the standalone Arduino CLI firmware for the **Waveshare ESP32-S3-RLCD-4.2** development board.
The device renders climate telemetry from onboard sensors and external SwitchBot thermo-hygrometers onto a 4.2-inch reflective LCD.
The list uses priorities. Priority 1 is the highest priority.
Do the work in priority order, unless the maintainer gives a different order.

## Rules for this file

- Write in ASD-STE100 Simplified Technical English.
- Add one entry for each open item. Do not give an entry a status. Each entry in this file is open.
- Remove an entry in the pull request that completes it. Describe finished work in `FEATURES.md`.
- Each entry names the code location, the goal, and the acceptance test.
- Each entry has a `Rank` line with the model, the total score, the four single scores, and the effort size. See "Rules for ranking".
- Put each entry in the priority that matches its total score. Order the entries inside a priority by total score, highest first. For equal scores, put the smaller effort first. Put a dependency above the entry that needs it.
- Priority 1 holds the most critical user-facing enhancements and core hardware integrations.
- Do not record review findings in this file. Name them in the review report and in the pull request description.

## Priority 1: Core Tooling and Calibration (Score 34–40)

- [ ] Panel pinning and deterministic connection timeouts in the macOS app
  - Rank: [Total: 35, Use: 8, Setup: 9, Harmony: 8, Safety: 10, Effort: M]
  - Location: `macos/RlcdCompanion/Sources/RlcdProtocol/LinkWatchdog.swift` (new), `macos/RlcdCompanion/Sources/RlcdProtocol/PanelPin.swift` (new), `macos/RlcdCompanion/Sources/RlcdCompanion/Transports.swift`, `macos/RlcdCompanion/Sources/RlcdCompanion/AppModel.swift`, `macos/RlcdCompanion/Sources/RlcdCompanion/Views.swift`, `macos/RlcdCompanion/Tests/RlcdProtocolTests/LinkWatchdogTests.swift` (new)
  - Goal: Let the user pin one panel. `BluetoothScanner` lists each peripheral that sends a valid telemetry frame or the console service, with its name, RSSI and the age of the last packet. The user selects one peripheral. `PanelPin` stores its `CBPeripheral.identifier` UUID through a small key-value protocol (`UserDefaults` in the app, an in-memory store in the tests). With a pin, the app shows only the frames of this UUID and connects the console only to this UUID. Without a pin, the app keeps the current behavior. A "Forget panel" button clears the pin. `LinkWatchdog` is a pure state machine with an injected clock. It fails a connection attempt after 10 s without "Console connected", a BLE write after 5 s without `didWriteValueFor`, and a command after 10 s without a chunk. Each failure gives one fixed reason text, closes the link and drops the queue. `BluetoothScanner.send` writes the chunks one after the other and waits for each write response. Thus the app never attaches to a neighbor panel and never waits without an end.
  - Acceptance test: `swift test` in `macos/RlcdCompanion` passes. New tests store, read and clear a pin in the in-memory store, reject a malformed UUID text, filter frames of a second UUID, and step `LinkWatchdog` with a fake clock: a connect timeout at 10 s, no timeout at 9.9 s, a write timeout at 5 s, a restart of the command timer by each chunk, and no timeout after a cancel. `swift build -c release` passes. The C++ host tests stay unchanged and pass.

- [ ] Structured `config.ini` editor with validation and batch `SET` in the macOS app
  - Rank: [Total: 35, Use: 8, Setup: 10, Harmony: 9, Safety: 8, Effort: M]
  - Location: `macos/RlcdCompanion/Sources/RlcdProtocol/ConfigSchema.swift` (new), `macos/RlcdCompanion/Sources/RlcdProtocol/Replies.swift`, `macos/RlcdCompanion/Sources/RlcdCompanion/AppModel.swift`, `macos/RlcdCompanion/Sources/RlcdCompanion/ConfigEditorView.swift` (new), `macos/RlcdCompanion/Tests/RlcdProtocolTests/ConfigSchemaTests.swift` (new), `docs/config.example.ini` (read only)
  - Goal: Replace the free-text `SET` field with a form. `ConfigSchema` holds one entry for each key of `DeviceConfigParser::KEYS`: the type (integer, decimal, enum, bit mask, name, MAC), the range or the enum values, the default value, the unit and one ASD-STE100 description. `ConfigSchema.validate(key:value:)` applies the same rules as `DeviceConfigParser`, for example 0 or 27 to 45 for `heat_alert_limit_c`, `C` or `F` for `temp_unit`, and `AA:BB:CC:DD:EE:FF` or empty for `slot1_mac`. The form groups the keys (climate, alerts, power, sensors, BLE), loads the values from the last `CONFIG` reply and marks each changed key. A diff sheet shows each change as `key: old -> new` before the apply. The apply sends one `SET` for each changed key in a fixed order, then one `CONFIG`. The first `ERR` reply stops the batch and names the key. The form disables the apply on BLE with `ble_console` below 2, and for each value that fails the validation or makes a line above 40 bytes. Thus the user edits the panel settings without a card reader and without knowledge of the key names.
  - Acceptance test: `swift test` in `macos/RlcdCompanion` passes. A new test reads `docs/config.example.ini` from the repository and fails when a key of the template is not in `ConfigSchema`, when a schema key is not in the template, or when a schema default differs from the template value. Other tests accept the limits and reject the values one step outside them for each numeric key, accept each enum value and reject another value, build the diff of two `ConfigReply` values, build the `SET` batch in the fixed order, and stop the batch at the first `ERR BAD_VALUE`. `swift build -c release` passes. The C++ host tests stay unchanged and pass.

- [ ] Nearby BLE sensor scanner and slot assignment in the macOS app
  - Rank: [Total: 34, Use: 8, Setup: 10, Harmony: 9, Safety: 7, Effort: M]
  - Location: `macos/RlcdCompanion/Sources/RlcdProtocol/Replies.swift`, `macos/RlcdCompanion/Sources/RlcdProtocol/SlotAssignment.swift` (new), `macos/RlcdCompanion/Sources/RlcdCompanion/AppModel.swift`, `macos/RlcdCompanion/Sources/RlcdCompanion/ScannerView.swift` (new), `macos/RlcdCompanion/Tests/RlcdProtocolTests/ScanReplyTests.swift` (new)
  - Goal: Add `ConsoleCommand.scan` and the parser `ScanReply`. It reads `BEGIN SCAN`, the header `mac,format,rssi,slot,temp_c,rh_pct,battery_pct`, one row for each MAC (format `WOIO`, `METER`, `BTHOME` or `ATC`, slot 1 to 3 or `-`, an empty battery field) and the optional `DROPPED,<N>` row. A scanner view lists the sensors with format, RSSI, temperature, humidity, battery and the current slot, strongest RSSI first. The app sends `SCAN` only on the USB serial link, because the firmware replies `ERR NOT_OVER_BLE` on BLE. It allows 10 s for the reply, because the scan takes about 4 s. The user selects one sensor and one slot. `SlotAssignment` builds `SET slot<N>_mac=<MAC>` with the `ConfigSchema` check, warns when another slot already holds the MAC, and then sends `CONFIG`. A "Clear" action sends `SET slot<N>_mac=` with an empty value, which the firmware accepts as "no fixed MAC". `ConsoleCommand.set` allows an empty value only for the keys `slot1_mac` to `slot3_mac`. Thus the user assigns a new thermometer without the serial terminal. This entry uses the schema of the entry "Structured `config.ini` editor with validation and batch `SET` in the macOS app".
  - Acceptance test: `swift test` in `macos/RlcdCompanion` passes. New tests parse a recorded `SCAN` reply with each format, an empty battery field, a slot `-` and a `DROPPED,3` row, reject a missing header, a bad MAC, an unknown format and a row with six fields, build the `SET` line for each slot and the empty clear line, refuse an empty value for another key, refuse a fourth slot, report a MAC that another slot holds, and refuse `SCAN` on the BLE transport. `swift build -c release` passes. The C++ host tests stay unchanged and pass.

## Rules for ranking

Rate each entry with the feature model. The model has four criteria. Each criterion has a value from 0 to 10. The total score is the sum, with a maximum of 40.
Effort does not add to the total. Give the effort as a size: S (one small pull request), M (one large pull request), L (several pull requests).

**Feature model:**
1. **Use:** How much does the feature help the user in daily climate monitoring? (0–10)
2. **Setup:** How much does it help the user configure, calibrate, or troubleshoot the device? (0–10)
3. **Harmony:** How many existing hardware components and firmware modules does it use or extend? (0–10)
4. **Safety:** How small is the risk of power drain, corruption, hardware wear, or data loss? 10 means no risk. (0–10)
